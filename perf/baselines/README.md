This baseline is captured by running `node tools/vscode-baseline/run.mjs`, which drives two disposable VS Code Extension Development Host windows, one over `perf/fixtures/large-files` and one over `perf/fixtures/monorepo`, via `--disable-extensions --extensionDevelopmentPath=tools/vscode-baseline` against an isolated per-run `--user-data-dir`/`--extensions-dir` profile (seeded with `chat.disableAIFeatures: true` and workspace trust disabled so the isolated profile's first-run Copilot sign-in prompt and trust dialog never block the automation); it measures the same scenario ids as the Codevo CDP perf runner using the closest available VS Code API per scenario, documented per entry by the `method` field because some behaviors are not directly scriptable (Quick Open ranking is approximated by an `executeCommand`-free `vscode.workspace.findFiles` enumeration proxy) or measure dispatch latency rather than paint/frame time (`type-command-await`), then writes `perf/baselines/vscode.json`. `definition-large-20k`/`references-large-20k`/`rename-large-20k` sample 10 different `*Kind` type declarations spread across `large-20k.ts` (not the same query repeated) and `completion-large-20k` triggers global, unfiltered-scope completion at a blank line so each repetition performs real language-service work; every one of the 10 repetitions of every provider scenario must individually return a non-empty result (a definition/reference array, a completion list, or a rename edit with entries) - one empty repetition converts the whole scenario to a `{ id, error }` entry instead of silently accepting a suspiciously-instant, no-op measurement - and the per-repetition result count is recorded alongside the timing in each entry's `resultCounts` array so the committed JSON itself is evidence the work happened, not just the timing. `tab-switch-cycle` pre-opens all five large-file tabs once before the six measured switch cycles start (mirroring the Codevo runner's own pre-open step in `perfScenarios.mjs`), so cycle 1 measures warm tab switches like every other cycle instead of folding a one-time cold document-open cost into the first sample.

Captured 2026-07-31 with VS Code 1.131.0 (commit `e4c7e7b1d6d060162f4aa7f8225271b67ce1df75`) on macOS 26.5.2, arm64 (Apple Silicon), against the `large-files@v2` / `monorepo@50pkg` fixtures generated by `npm run perf:fixtures` (fixture version recorded verbatim in `perf/baselines/vscode.json`'s `fixtureVersion` field). `large-files@v2` adds a minimal `package.json`/`tsconfig.json` to `perf/fixtures/large-files` so the directory can be opened as a real workspace/project (fixes C1); this changes the large-files TypeScript language-service context from VS Code's inferred-project mode to an explicit project, which is why this baseline is not directly comparable to any capture taken against `large-files@v1` fixtures (the ones without markers). `references-large-20k` and `rename-large-20k` land in the low single-digit milliseconds because the fixture's `*Kind` types are declared and used only within a single self-contained file (no cross-file imports), so TypeScript's language service resolves them from an already-warm per-file symbol table; this was verified to be real (non-empty on every repetition, assertion-checked, `resultCounts` all greater than zero) work rather than a no-op short-circuit, not a measurement bug.

Provenance: `node tools/vscode-baseline/run.mjs` completed this capture fully end to end, unmodified, on the first run - both fixture roots, no manual intervention. Earlier captures of this baseline needed a manual `code`-launch workaround because the isolated `--user-data-dir` lived under a long `os.tmpdir()` path (`/var/folders/.../T/codevo-vscode-baseline-user-data-<label>-<timestamp>`); the resulting IPC Unix-domain-socket path (`<user-data-dir>/1.<version>-main.sock`) exceeded macOS's ~103-character `AF_UNIX` path limit, which made the freshly spawned VS Code process treat itself as a duplicate of an already-running instance and self-terminate (`Lifecycle#kill()` in its own verbose log) within about a second of launch - not a crash, and not a sandbox/process-tree constraint as an earlier capture round had suspected. `run.mjs` now derives its isolated profile directories from `/tmp` directly instead of `os.tmpdir()` on non-Windows platforms (see `ipcSafeTmpDir()`), which keeps the socket path short enough to bind. With that fixed, `run.mjs` is a genuinely reliable, reproducible entry point on macOS; no direct `code` launches or manual JSON merging were needed for this capture.
