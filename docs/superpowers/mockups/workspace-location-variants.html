Where am I working?

Design proposal for the owner's note: "I don't quite like this part. I can't tell how and when I'm in which workspace." Three variants that make the working location obvious at a glance, compared against a faithful recreation of today's UI. Graphite · Teal palette, real --cv-* tokens. Use the state switcher above (keys 1-4). Every frame on the page follows it.

What the screenshot shows

The sidebar header (AgentRailHeader): the Search field, then a 16px "E" monogram button, Add project (folder +) and New thread (pen). The "E" is AgentProjectFilterMenu, i.e. the project filter showing editor. Below it: "Saved conversations".

What the app actually knows about "where"

  • Machine: This computer, or a connected server by name (remote runner).
  • Project: label and root folder.
  • Checkout: in place (the project folder itself, your working copy, shared with the editor and other in-place threads) or worktree (<repo>/.worktrees/<task-id> on branch agent/<task-id>, created from the chosen base branch). On a server: server checkout or a worktree there.
  • Branch: in place = the checkout's current branch (live, it changes if you switch it); worktree = agent/<task-id> with ahead/behind the primary branch from the ship status. For server threads this view doesn't know the branch today, so no variant shows one.
  • Right panel: Files, Git and Terminal follow the selected thread's checkout (the worktree path for worktree threads). For a new thread they follow the chosen project. When the active workspace differs, they show "Switch".

What's confusing, concretely

  1. One letter, no name. The monogram is the first letter of the project name. editor and eshop both render "E". With "All projects" it becomes a plain folder icon that looks like the Add project button next to it.
  2. It looks like a filter but does four things. Picking a project in it (a) filters the list, (b) sets where New thread / ⌘N starts (visible only in a tooltip), (c) switches the active IDE workspace behind the right panel (onSelectProjectEnvironment) and (d) reopens that project's last thread.
  3. It changes under you. Clicking a thread from another project moves the filter to that project (agentRailFilterFollowingProject) and switches the workspace (selectWorkspace) with no cue. That's the "when" in the complaint.
  4. The actual location is scattered and uses different words. The header shows only the project. The composer footer says "Local checkout" / "Server checkout" / "New worktree", and after sending it still says "New worktree" for a worktree that already exists, with no branch. Sidebar rows say "in place" / "worktree" or the branch. "This computer" appears only inside a menu.
  5. The right panel never says what it shows. "Thread files" / "Project files" gives no folder or branch, so you can't tell your working copy from a worktree.
  6. The key distinction is never stated plainly. The distinction that matters most, "the agent edits my files" vs "the agent edits an isolated copy", is never said in those terms.

Shared rules in all three variants

  • Filter ≠ location. The sidebar project filter only filters rows and is labelled by name. You change where you work only by selecting a thread, starting a new thread in a project, or using "Switch project" in the palette.
  • One vocabulary everywhere: In place, Worktree, the server name. The machine is named only when it isn't this computer. Before sending, the machine picker appears only if a server is configured.
  • After sending, the location shows the real checkout (agent/agt-…), never "New worktree".
  • When the location changes, the location element briefly tints (1.3s, off under reduced motion). No toasts. Switch states above to see it.

Variant A

Location breadcrumb

The top bar breadcrumb becomes project / checkout·branch / thread. For a server thread the segment names the server. Clicking the segment opens its details.
The composer shows the location picker only before the first send. After that the header is the single source, so the footer stays empty.
The right panel repeats the same token above its content, with the folder path. The sidebar gets a labelled "All projects" filter that never switches the workspace.

What changes

  • The "E" monogram button is removed. Under the search field there's a text filter, "All projects ⌄" (or "editor ⌄"), that only filters rows.
  • Header crumb segments: [E] editor (click to start a new thread in any project) / main · in place, agent/agt-… · worktree or build-box · server checkout, each with its glyph (click for details) / title.
  • Before sending, the crumb shows the pending choice with a dashed outline and the composer shows the picker with the same words. Once you send, the dashed crumb turns solid.
  • The right panel shows a scope line with the same token and the folder path, so you can see it's the same checkout.
  • Sidebar row line 3 uses the same token vocabulary.

Trade-offs

  • + One quiet line at the top, where IDEs put context. It stays visible while you scroll and doesn't grow the composer. (t3code itself keeps its header to project / title and puts the checkout in a strip under the composer, see How t3code does it.)
  • + One source of truth plus one echo, and both use the same component.
  • − Long titles plus long worktree branches compete for header width. The branch truncates in the middle (agent/agt-…7ede) and the full value is in the popover.
  • − The in-place vs worktree consequence is mostly in the popover. Mitigation: B's one-line hint before the first send (see the recommendation).
Variant B

Run line under the composer

The composer footer becomes a readable sentence: Running on This computer · editor · worktree agent/agt-… · 2 ahead of main, led by a colored kind dot.
Before sending, every word is a picker, with a one-line consequence below ("Edits land in your working copy").
The header gets only a small kind pill after the title. The right panel starts with the same dot and checkout line.

What changes

  • The sidebar gets the same labelled filter as A.
  • The drawer row under the composer is replaced by the run line. It's editable before the first send and read-only afterwards, but it stays visible.
  • Kind dot colors: in place = neutral --cv-fg-muted, worktree = --cv-accent, server = --cv-syn-num. Color is always paired with a word.
  • The header pill ("In place" / "Worktree" / "build-box") is a compact reminder when the composer is scrolled out of focus.

Trade-offs

  • + The most explicit, and it sits exactly where you decide and type. The consequence sentence teaches the model.
  • − A permanent sentence under every composer. t3code also keeps a permanent strip there, but it holds only icons and two-word labels. A full sentence reads heavy in long sessions.
  • − The location is at the bottom while the right panel's echo is at the top, so the eye has to travel to compare them.
Variant C

Workspace switcher in the sidebar

The screenshot area itself becomes a full workspace switcher card: project name, then checkout·branch (and the server name for a server). It's the one thing the right panel and ⌘N use.
The filter is split out into a small "This project | All" toggle. Rows carry location tokens.
The header keeps project / title plus a kind pill. The right panel starts with the same project ▸ checkout line.

What changes

  • The monogram button becomes a 48px card at the top of the sidebar. Clicking it opens the project switcher (the same list as today's filter menu, but choosing a project here is explicitly a switch).
  • The card's second line follows the selected thread's checkout, so it updates (with a tint) when you pick a thread elsewhere.
  • "This project | All" only filters rows.
  • The composer footer keeps pickers with fixed copy, and the locked state shows the real checkout.

Trade-offs

  • + Fixes the exact spot the owner pointed at, and feels familiar from VS Code / Linear workspace switchers.
  • − The sidebar lists threads from all projects, while the card names one project. When you browse "All", the card and the row you click disagree until you click.
  • − The location sits far from the conversation, which is where you look while you work. It's also hidden when the sidebar is collapsed.

How t3code does it

Recreated from t3code's source (pingdotgg/t3code main at c2fa9fc, 2026-09-30, one day after v0.0.44). t3code's labels and layout, drawn with Codevo tokens. Paths are relative to apps/web/src/components/ unless noted.
t3code has no "active workspace". Where a thread works belongs to the thread itself. The header leads with the project. Machine, checkout and branch sit in a thin strip under the composer. The sidebar's project button only filters.
Remote exists as environments: other machines running the T3 server, picked with "Run on". The right panel (Diff, Files) follows the thread's worktree or the project root but never says which one it shows.

Markers

1The project button filters rows only. It stays on "All projects" in every state, because selecting a thread never moves it.
2The project always leads the header. Clicking it starts a new thread in that project. Nothing in the header names the checkout, branch or machine.
3The composer's context strip is the one place that states the location. It shows pickers before the first message, muted labels afterwards, and a branch picker that stays live.
4Diff and Files read the thread's worktree (or the project root) without naming it. Only "Branch changes" shows the head ref.

What to take from it

  • Location is a thread property. There's no workspace state that can drift away from the thread, so the "when did it change" problem can't happen.
  • One compact strip, same slot in every state. It shows Run on | checkout, then the branch on the right. A strip under the composer turned out to be what t3code chose, and it stays calm.
  • The filter only filters. It's persisted, never follows the selection, and "New thread" asks which project instead of guessing.
  • Gaps for Codevo: the right panel never names its checkout. The words drift too: "Current checkout" before sending, "Local checkout" after, and "Local checkout" even on a remote machine.

Refinement

C + t3code

C's card stays at the top of the sidebar, but it becomes a mirror of where the selected thread (or draft) runs, with a "New thread in…" menu. It never switches or filters on its own.
t3code's composer strip replaces C's footer. The filter becomes a named, persisted project filter. Rows always show the branch. The header drops the pill.
Kept for Codevo: remote runners are named everywhere, and the right panel says which checkout it shows, in the same words as the strip. Δ marks each difference from plain C.

Differences from plain C

Δ1The card mirrors the thread. It shows the project, then the checkout and branch (plus the server for a server). Clicking it opens New thread in… and location details. Picking a project there starts a draft in that project. Nothing switches behind the right panel. (t3code: the header's project crumb and ✎ start threads, and there's no active-workspace state.)
Δ2The filter is a named project filter ("All projects ⌄" / "editor ⌄"). It's persisted and never follows the selected thread. It replaces C's relative "This project | All". (t3code Sidebar.tsx:2394.)
Δ3Rows always show the branch on line 3, with the kind glyph and +/− stats. The server is named on line 1. (t3code Sidebar.tsx:1951.)
Δ4The header is project / title only, with no pill. The project crumb starts a new thread in that project. (t3code chat/ChatHeader.tsx:407.)
Δ5t3code's context strip replaces the footer. The machine comes first (only when a server is configured), then the checkout, with the branch on the right. These are pickers before the first send and muted labels afterwards, with the same words before and after, unlike t3code.
Δ6The panel line uses the strip's exact words plus the path. t3code has nothing like this. It's kept from C and aligned in wording.
Δ7Borrowed notice for in-place threads whose checkout moved to another branch since the thread last ran:
Branch changed · was main, now feature/sidebar
t3code: ChatView.tsx:6541-6572 (the "Branch changed" notice with "Restore branch"), BranchToolbar.logic.ts:246-260.

Decisions for the owner

  1. Branch after start. t3code keeps the branch picker live on a started thread. Picking a ref runs git switch in the thread's checkout (your working copy, for in-place threads), and moving to another worktree stops the session. The mockup shows it read-only plus the Δ7 notice. Should it be live or read-only?
  2. Words. t3code says "Current checkout" in the picker, then "Local checkout" / "Worktree" once locked, and "New worktree" / "Previous worktree". The mockup uses Local checkout · New worktree · Worktree · Server checkout everywhere, dropping "In place". Is that OK?
  3. New thread with several projects. t3code opens a "New thread in…" picker (Shift-click creates in the current project). Codevo's ⌘N creates immediately in the card's project. Which one?
  4. Filter. A pinned, named project (t3code, shown) or C's relative "This project" (which changes the list whenever the card follows another thread)?
  5. "Previous worktree". Should the checkout picker offer t3code's "Previous worktree (branch)" to continue in the last worktree of the project?
  6. The card follows the thread, even from a filtered list. When you open a thread through search or the palette from another project, the card changes but the filter stays. Confirm.

Recommendation: Variant A, plus two small pieces of B

Put the location in the header breadcrumb (project / checkout·branch / thread), echo it at the top of the right panel, and turn the sidebar monogram into a labelled filter that only filters. From B, keep the one-line consequence under the pre-send picker ("Edits land in your working copy" / "Creates agent/… from main in .worktrees/"). From C, keep the location tokens on sidebar rows (A already includes them).

Why: the header and the right panel sit on the same top line, so you can compare them at a glance. The location stays visible while you scroll and the composer doesn't grow. B is clearer but permanently heavier. C fixes the literal spot but creates a second source of truth that contradicts the all-projects list.
