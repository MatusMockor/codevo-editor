POST /orders creates duplicate orders when the mobile client retries after a timeout (trace attached). Add Idempotency-Key support so retries replay the first response. Keep it in middleware, and cover it with tests.

The client times out at 5s but the handler commits after the payment hold (p95 about 6.8s), so each retry inserts a fresh row.

A key scoped per tenant avoids cross-tenant replay. Store the fingerprint of the body too, so a reused key with a different payload is rejected instead of silently replayed. Only cache non-5xx responses.

POST /orders now honors an Idempotency-Key header. The first request with a key runs normally and its response is stored; retries with the same key replay that response instead of creating a second order.

  • New idempotency() middleware keys on tenant + header and keeps the response for 24 hours.
  • The route at src/routes/orders.ts:42 mounts it before the handler.
  • Reusing a key with a different body returns 422 with idempotency_key_reused.
